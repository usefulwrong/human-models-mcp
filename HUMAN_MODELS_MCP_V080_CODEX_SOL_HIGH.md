# UsefulWrong / Human Models MCP — Codex Sol High handoff v0.8.0

**Название итерации:** Anatomical Grounding & Evidence v1  
**База:** публичный `usefulwrong/human-models-mcp`, версия v0.7.1 (или фактический текущий `main`, если новее).  
**Окружение:** Linux, Docker/Compose, RTX 3070 Ti 8 ГБ; физика MuJoCo выполняется на CPU, GPU — только для поддерживаемых этапов рендера.  
**Режим:** автономное исследование → минимально полная реализация → научная и инженерная приёмка; **без Git commit/push/tag/release**, оператор делает это сам.

## Зачем нужна эта итерация

В v0.7.1 уже работают MuJoCo 3.17.0, MS-Human-700, 14 MCP-инструментов, сохранение всех доступных мышечных трасс, region-specific tendon-path layers, OpenUSD → Blender 4.5.15, проверка геометрии на уровне преобразований, визуальные профили, паспорта источников. Не переписывай ни один из этих контуров с нуля.

Главный пробел: **актуаторы и пути сухожилий не являются настоящими объёмными мышцами**. Внешние анатомические источники присутствуют лишь в `visual_sources.json`, их регистрация не верифицирована. Не хватает независимого сравнения движения с motion capture и строгой интерпретации «уверенности» результата.

**Главный измеримый результат v0.8:** хотя бы одна анатомическая мышечная группа из проверенного внешнего источника корректно зарегистрирована на существующую кинематику, визуализируется в нескольких реальных состояниях `pushup` / `pushup_palms`, и результаты имеют машиночитаемый паспорт достоверности. Это новый *анатомический визуальный слой*, а не обещание деформационной FEM-механики. Отдельно создаётся рабочий интерфейс импорта/сравнения референсного движения.

## P0 — прозрачный паспорт достоверности (Evidence Contract)

Добавь совместимый **пер-утверждение/пер-артефакт** формат свидетельств, не ломая существующие MCP-ответы и `passport.json`.

Минимум для каждого вычисляемого вывода:

- `claim_id` / величина / значение / единицы / временное окно / side / структура;
- `source_model`, версия, pin, SHA, сценарий, control mode, code SHA и идентификатор вычисления;
- `computed_status` (completed/failed/not_run);
- `numeric_checks` с индивидуальными PASS/FAIL/NOT_RUN и порогами;
- `anatomical_mapping_status` (native / verified_registration / illustrative / unavailable);
- `reference_comparison` (dataset, версия, процедура согласования, метрика, количество пригодных кадров, результат либо NOT_AVAILABLE);
- `scope_limitations` и `known_confounds`, например external joint assistance, simplified contacts;
- `evidence_class`: `computed_only`, `internally_checked`, `compared_with_external_data`, `externally_validated_for_named_claim`;
- `confidence_explanation`: чем это подтверждено и чего **не** доказывает.

**Не придумывай проценты уверенности (97%, 0.92 и т. д.) без отдельной калибровки и верификации.** PASS геометрического теста — не подтверждение достоверности мышечных сил реального человека. Сохрани `computed` отдельно от `validated`. Некорректный или неподдерживаемый вывод должен возвращать `unsupported` / `unvalidated`, а не правдоподобный текст.

Возможно реализовать отдельный read-only MCP-инструмент `get_evidence(run_id, claim_id?)` или расширить существующий `get_result` без увеличения числа инструментов — выбери самый простой согласованный вариант. Для средств без ИИ — CLI/Python.

## P0/P1 — настоящая 3D-геометрия мышц

**Выбери одну ограниченную область, связанную с отжиманиями**, предпочтительно грудные мышцы, либо альтернативную группу с более качественными доступными исходниками и понятной картой костных ориентиров. Не обещай сразу 700 объёмных мышц. Не вводи новые физиологические движки.

1. Исследуй первичные источники. Первый кандидат — Z-Anatomy / BodyParts3D (пообъектная проверка лицензий CC BY-SA и сторонних материалов), запасной — другой источник с документированной геометрией. HRA годится для референсной анатомии органов и костей, но **не** объявляй его готовой моделью грудных мышц.
2. Не загружай весь атлас в git и не смешивай CC BY-SA производную геометрию с MIT-кодом так, будто это одна лицензия. При невозможности открытого распространения дай воспроизводимый *опциональный* importer с локальным cache, sha256, источником, режимом offline и license gate.
3. Сделай явную карту: оригинальный анатомический идентификатор → объект/mesh → несколько проверяемых bone/landmark correspondences модели → трансформация в MuJoCo/Blender, единицы и handedness. На каждом шаге логируй реальную ошибку регистрации, проверку mesh integrity, положение границ, пересечения, стабилизацию между кадрами.
4. Визуализируй объёмный объект на `start`, `bottom`, `return` одной и той же вычисленной траектории и, если возможно, экспортируй короткую анимацию. Отделяй **rigged/skinned визуальную деформацию** от рассчитанной механики ткани. Если нет FEM/контракта свойств материала, запрещено утверждать `computed muscle strain`, `tissue stress`, `clinical force`.
5. Цвет мышцы может отражать сохранённую активацию **конкретных источниковых актуаторов** только при документированной карте агрегирования. В иных случаях нейтральный материал и пояснение `activation mapping unavailable`.
6. Если регистрация недостоверна, не обозначай слой `verified`. Оставь `illustrative`/`unsupported` и не делай вид, что успешный рендер подтверждает анатомию.

**Критерий P0:** как минимум один настоящий объёмный анатомический объект корректно загружается, имеет источник/лицензию и проверяемую регистрацию в неподвижной позе.  
**Критерий P1:** тот же объект обоснованно движется вместе с сохранёнными состояниями из реального сценария, с отчётом о численных остатках и статусе метода визуальной деформации. Если движения нет, выпуск не называть полноценным динамическим анатомическим слоем.

## P1 — reference datasets и воспроизводимое сравнение движения

Разработай небольшой адаптер движения в *отдельной необязательной подсистеме*, а не ещё один RAG. Основной кандидат: **Fit3D**, где есть Vicon/3D joints и видео упражнений, включая отжимания. Лицензия Fit3D — некоммерческая, персональная/ограничивающая перераспространение: **никаких исходных видео, mocap или производных данных Fit3D в репозитории, Docker-образе, CI или GitHub Releases без письменного разрешения**.

- Исследуй и зафиксируй точную лицензию; поддержи *manual BYO dataset* вне репозитория, без обхода авторизации. Ищи, если нужно, второй совместимый с открытым распространением датасет.
- Создай нормализованный контракт `reference_motion` (source/license, fps, координатная система, joint IDs, camera, units, time, subject/motion metadata, provenance); проверяй NaN, пропуски, оси, ориентацию, разрешение и ошибку ретаргетинга.
- Реализуй **реальный** конвертер для одного поддерживаемого открытого/предоставленного формата и интеграционный тест на доступных данных. Синтетический fixture допустим для контракта, но не считается независимой валидацией.
- Сравнивай сопоставимые величины: формы временных траекторий суставов, углы после явного сопоставления осей, высоту/позу корпуса и тайминг фаз. При необходимости DTW, но показывай временное искажение. Согласуй масштаб и антропометрию; отчёт о геометрической привязке обязателен.
- Motion capture сам по себе **не даёт** измерений мышечных сил, EMG, давления и травмоопасности. Нельзя оценивать эти величины по отсутствующим каналам.
- Создай overlay-визуализацию `reference skeleton vs simulated skeleton` и количественный `comparison.json`/график с фактическими метриками. Если датасет недоступен, выдай `NOT_RUN: LICENSED_DATA_NOT_PROVIDED` и рабочую инструкцию, как пользователь сможет предоставить свою копию. Не объявляй внешнюю валидацию пройденной.

## P1 — процедурный Blender без генерации кода агентом

Blender Python уже имеется (`blender_scene.py`), поэтому **не переписывай** экспортёр OpenUSD и систему проверки геометрии. Введи именованные типизированные render recipes поверх существующих `render_result`, `list_render_profiles`, `get_render_job` и `get_render_artifact`.

Рекомендуемые рецепты:

- `pushup_scientific`: скелет, суставные оси, контакты, диаграммы;
- `pushup_muscle_paths`: все относящиеся к задаче путевые актуаторы с legend и units;
- `pushup_anatomy`: только верифицированные/явно иллюстративные объёмные мышцы;
- `pushup_reference_overlay`: рассчитанная поза и допустимый внешний референс;
- `pushup_cinematic`: те же сохранённые состояния с другим светом, камерой и материалами.

Один запрос от ИИ должен запускать Python-процедуру/встроенный orchestration, а не вызывать LLM для вычисления каждого кадра и не заставлять агента писать `bpy`-код. Никакого arbitrary Python через MCP. Все параметры ограничены схемой и ресурсным бюджетом. Переиспользуй trajectory, модель, scene и геометрию; кешируй по content hash, обеспечь idempotency и корректное восстановление неудачного рендера. Повторный рендер не пересчитывает физику.

Допустимо дать один высокоуровневый инструмент `create_scientific_visualization(run_id, recipe, options)` **только если** он реально уменьшает вызовы и корректно использует существующую очередь. Тот же API должен быть доступен CLI/Python; без лишнего фреймворка.

Инструмент возвращает компактное структурированное резюме и идентификаторы/пути к доказательствам; изображения и видео передаются как артефакты, не base64-дампом в контекст агента.

## P1 — skills и документация для агента

Обнови существующие 4 skills, особенно `scientific-interpretation` и `scientific-visualization`.

Агент обязан: узнать возможности → выбрать сценарий и референс → выполнить расчёт → проверить named gates → проверить scope соответствия запроса и модели → выбрать render recipe → получить визуализацию и evidence → сделать вывод только в пределах подтверждённых величин.

Запреты: `simulation PASS = human-safe`, `muscle activation = EMG`, `registered mesh = FEM`, `render completed = biomechanical validation`, `atlas can be freely redistributed`, `aesthetic overlay = measured anatomy`.

## E2E и фальсифицирующие тесты (обязательно)

1. `make test`, `make e2e`, `make pushup-e2e`, `make render-e2e`, `make visual-regression` (если применяется), затем повторить после финальной правки. Не менять/не отключать старые тесты для PASS.
2. Из **чистой копии**: модель → `pushup`/`pushup_palms` → сохранённая траектория → импорт одной реальной мышцы → регистрация на 3+ кадрах → render recipe → Blender → PNG/GIF/MP4 → evidence. Проверить с настоящим MCP-клиентом и независимо через CLI.
3. Преднамеренно испорченные единицы, оси, 3D landmarks, версия модели, лицензия, dataset metadata, размер mesh и файл trajectories должны давать явный FAIL, не красивую картинку.
4. Состояния MuJoCo и исходные численные артефакты должны оставаться **побайтово неизменными** после повторного рендера, при получении ошибок и CPU/GPU fallback.
5. Контроль состояний `start/bottom/return`, изменение позы и волокон в динамике, корректность слоёв и источников. Сделай контакт-лист и автоматические проверки геометрии/временных индексов; визуально проверь кадры.
6. Совместимость с RTX 3070 Ti 8 GB, ограничение VRAM, отдельные результаты для CPU/GPU; отсутствие GPU не должно маскироваться под GPU PASS. Если Docker/модель/данные недоступны — `BLOCKED` для соответствующего этапа.
7. Проверка умышленно неправдоподобного утверждения: агент не должен описывать анатомическую объёмную деформацию как рассчитанную, а синтетическое движение как подтверждённое mocap.
8. Измерь число MCP-вызовов/размер возвращаемого текста для типового сценария до/после добавления рецептов. Цель — меньше лишних вызовов, не выдумывай «нулевой расход токенов» при общении с LLM.

Статусы:
- `RESEARCH_PREVIEW_READY`: P0 выполнены, реальный MCP→MuJoCo→Blender E2E прошёл, обязательные научные оговорки и лицензии корректны.
- `PARTIAL`: часть инфраструктуры работает, но анатомическая регистрация или проверка не подтверждена.
- `BLOCKED`: обязательный этап не проверен из-за среды/данных/лицензий.
- `FAIL`: воспроизводимая регрессия или критически ложные заявления.

Не называй `validated anatomical muscle mechanics` то, что является зарегистрированной визуальной оболочкой. Если нельзя достоверно завершить весь объём, закончи минимальный законченный вертикальный срез, покажи конкретные недостающие доказательства и предложи следующую итерацию. **Не выполняй Git commit/push/tag — оператор делает самостоятельно.**
